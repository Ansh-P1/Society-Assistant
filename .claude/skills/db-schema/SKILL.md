# Database Schema Conventions

Rules for anything that touches PostgreSQL: migrations, table definitions,
and queries. Keep new tables/columns consistent with these rather than
matching whatever ORM default is easiest.

## Naming conventions

- Tables: plural, `snake_case` - `users`, `complaints`, `complaint_status_history`,
  `notices`.
- Columns: `snake_case` - `created_at`, `resident_id`, `is_important`,
  `threshold_days`.
- Foreign keys: `<singular_referenced_table>_id` - `resident_id` (references
  `users.id`), `complaint_id` (references `complaints.id`), `actor_id`
  (references `users.id`, used in history rows since the actor may be either
  role).
- Booleans: prefixed `is_`/`has_` - `is_important`, `is_overdue` (if ever
  materialized - see db-schema note below on overdue being computed, not
  stored).
- Timestamps: `created_at`, `updated_at`, both `timestamptz`, not `timestamp`
  (avoid timezone bugs). Every table gets `created_at`; only give a table
  `updated_at` if rows are actually ever updated in place (history tables do
  not get one - see below).
- Enums (status, priority, category, role): store as a Postgres `enum` type
  or a `varchar` with an app-level check constraint - pick one approach and
  apply it consistently across `complaints.status`, `complaints.priority`,
  and `users.role`. Prefer Postgres native `enum` types for these fixed,
  rarely-changing value sets.

## Migration file naming

Sequential, timestamp-prefixed, descriptive, one logical change per
migration:

```
migrations/
  20260101000000_create_users.sql
  20260101000100_create_complaints.sql
  20260101000200_create_complaint_status_history.sql
  20260101000300_create_notices.sql
  20260101000400_add_indexes.sql
```

(If using Prisma, this becomes Prisma's own `prisma/migrations/<timestamp>_<name>/`
folders generated by `prisma migrate dev` - don't hand-name those, but keep
each migration scoped to one logical change the same way.)

## Append-only history table

`complaint_status_history` (or the ORM-equivalent model) is **insert-only**:

- No `UPDATE` or `DELETE` statements ever target this table from application
  code.
- No `updated_at` column - a history row is immutable from the moment it's
  written, so "when was this row last changed" is a meaningless question.
- No unique constraint that would force an upsert - every status change is
  a new row, even if (hypothetically) the same transition happened twice.
- If a mistake needs correcting, it's corrected by inserting a new
  compensating row with a note, never by editing or deleting the wrong one -
  the history must remain a true audit log.

See [[complaint-lifecycle]] for the full column list and the transition
rules this table enforces at the application layer.

## Required indexes

Admin views filter/sort by these fields constantly, so index them:

- `complaints(status)` - admin filters by status, and overdue detection
  filters on `status != 'Resolved'`.
- `complaints(category)` - admin filters by category; dashboard groups by it.
- `complaints(created_at)` - admin filters by date range, overdue detection
  and default sort both order by this.
- `complaints(resident_id)` - residents list only their own complaints.
- Composite `complaints(status, created_at)` is worth adding once the
  overdue query is written, since that query filters on status and sorts on
  created_at together.
- `complaint_status_history(complaint_id)` - every "get history for this
  complaint" lookup filters on this.
- `notices(is_important, created_at)` - notice board pins important notices
  to the top, then sorts the rest by recency.

Add indexes in the same migration that adds the column/table where
practical, rather than batching them all into one migration at the end.
